El concepto

Qué es y por qué existe

El problema, el enfoque y el alcance real del proyecto.

Control local de dos válvulas SONOFF SWV-NH y un interruptor ZBMINIL2 mediante Zigbee2MQTT y Mosquitto, sin nube ni cuenta de fabricante. Una CLI en Python y un menú interactivo permiten listar dispositivos, abrir o cerrar válvulas, consultar caudal y batería, y emparejar nodos; cada comando despierta al dispositivo dormido y espera la confirmación real del estado. Apunta a instalaciones domésticas o pequeñas parcelas con un servidor Linux y un dongle Zigbee.

Demuestra que un end device a batería puede comandarse de forma fiable si se respeta su ciclo de sueño, y documenta métricas medidas en Raspberry Pi 4: 0,5–2 s de confirmación con la válvula despierta y 2–8 s dormida, ~100 MB de RAM y cero tráfico a Internet. No incluye planificador de riego, autenticación MQTT, alta disponibilidad ni TLS; la confirmación depende de un timeout y puede fallar aunque el riego se ejecute.

Cómo leer esta ficha

Los tropiezos salen de la bitácora y de las versiones tempranas. La evaluación usa seis criterios fijos, de 1 a 5, y no premia la espectacularidad: premia que el proyecto se pueda reproducir y entender.

01 — La idea

El agua no necesita una cuenta en la nube

Zigbee2MQTT y Mosquitto alcanzan para controlar el riego sin depender de un fabricante ni de internet.

El problema

Muchas válvulas inteligentes requieren una app del fabricante y una cuenta en la nube. Si se cae internet o el servicio, el riego queda inaccesible. Además, los datos de uso salen de la casa.

La solución

Un coordinador Zigbee local, Zigbee2MQTT en Docker y Mosquitto. Dos válvulas SONOFF SWV-NH y un interruptor ZBMINIL2 se controlan por MQTT con una CLI y un menú interactivo.

Tropiezos

Los tropiezos, documentados

Lo que no funcionó en las primeras versiones, con la corrección aplicada.

v1 · primer comando

El converter usa ON/OFF, no OPEN/CLOSE

Los primeros envíos no hacían nada porque la válvula SWV expone state ON/OFF. Se validó STATE_OPTIONS y se tradujo open/close a ON/OFF en el CLI.

v1 · válvulas dormidas

Comandos intermitentes por el ciclo de sueño

El set ZCL caduca a los 10 s y la válvula duerme; por eso el resultado era «a veces sí». Se hace un get para despertarla, se descarta el payload cacheado y se espera el state exacto, con lo que la confirmación pasó a 2–8 s.

v1 · emparejamiento

permit_join necesitaba el campo time

En Zigbee2MQTT 2.x la ventana no abría o quedaba abierta para siempre si no se enviaba time. Se añadió el campo y se documentó que Ctrl+C durante la espera deja la ventana activa.

v1 · entrevista Zigbee

El ZBMINIL2 no emparejaba a distancia

El interview fallaba con «can not get node descriptor» lejos del dongle. Hubo que emparejar el interruptor junto al coordinador y luego reubicarlo.

Preguntas

Lo que suelen preguntar

¿Qué controla?

Dos válvulas SONOFF SWV-NH y un interruptor ZBMINIL2 a través de Zigbee2MQTT y Mosquitto, con una CLI y un menú en Python.

¿Qué no hace?

No programa riegos, no gestiona varios hosts ni autentica MQTT, y no cifra el tráfico local. La confirmación puede vencer por timeout aunque la válvula haya actuado.

¿Cómo se despliega?

Se levantan Zigbee2MQTT y Mosquitto con Docker Compose, se apunta el dongle por /dev/serial/by-id y se emparejan los dispositivos. Luego se instala paho-mqtt y se usa valvulas.py o menu_valvulas.py.

¿Qué se puede reutilizar?

El patrón get + descartar caché + set + esperar state para dispositivos dormidos, la validación de converters y el menú con conexión persistente.
